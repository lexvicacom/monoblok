Examples

Every example here is a real file in the repository, shown in full and checked with monoblok --validate. The level labels indicate the amount of configuration and number of forms involved.

How to run them#

Each example in examples/ has a matching .sh script that starts a temporary monoblok, subscribes, publishes sample data and prints what arrived. The scripts need the NATS CLI.

To run a patchbay yourself, pass the file to monoblok and use any NATS client:

To see what a file does with no server at all, pipe SUBJECT|payload rows through --soundcheck. The site build uses this command to generate the transcripts on these pages:

When testing with nats pub, pass negative bodies after --, for example nats pub sensors.temp -- -5.

Round and squelch#

Starter The canonical first rule. A jittery sensor publishes readings that differ in the second decimal place; subscribers only care when the value really moves.

payload-float parses the payload as a number, round trims it to one decimal place, squelch passes it only if it differs from the last value seen on this subject, and publish! sends it to <subject>.stable. When squelch suppresses, it returns nil, and publish! on nil does nothing.

Seven readings in, three out. State is per subject, so sensors.temp and sensors.humidity are deduplicated independently by the same rule.

Last-value cache#

Starter A normal subscriber sees nothing until the next publish. The last-value cache fixes that: opt subjects in with (lvc ...), and a subscriber to $LVC.<subject> gets the cached value immediately, then live updates.

Single-quote any subject starting with $ so your shell does not try to expand it. The cache pairs particularly well with conditioning rules: a subscriber to $LVC.sensors.temp.stable gets the most recent rule-produced value on connect, not the raw input. More in LVC, stats and snapshots.

A tour of the primitives#

Starter This is the patchbay loaded on the public demo server. It includes examples from each form family: squelch for value dedup, deadband for "ignore small wobbles", moving-avg for smoothing, delta for per-tick change, transition for boolean edge detection, rising-edge for one-shot crossings, hold-off for time-based rate limiting, and count! for tallies.

Try it against the public server without installing anything:

The first terminal prints a handful of derived subjects: demo.sensors.temp.stable, .delta, .smoothed, .delta-abs. Each one comes from a different patchbay rule applied to the input. The client publishing the raw readings does not know any of those rules exist.

The same file exists as demo.yml and demo.json if you want to compare the three spellings rule by rule. The demo server is shared and public with no auth, so do not send secrets. The demo walkthrough has more to try, and the live demo page drives the same server from your browser.
