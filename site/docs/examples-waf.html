Filtering and privacy

Most examples reshape a stream. These decide what is allowed through: a WAF for NATS that scans payloads, holds back readings above the rolling p99 and flags a flooding subject, and a patchbay that strips identifiers from patient records before they are forwarded.

A WAF for NATS#

Intermediate A web application firewall sits in front of a web server and decides which requests get through. This patchbay does the same job for a NATS cluster. Publishers connect to monoblok instead of the cluster and publish under in.>; three rules decide what continues as clean.> and what is reported on waf.>.

Rules see a message's subject and payload. They do not see which connection published it, so every decision here is per subject, not per client.

Payload scan#

The first rule is stateless. contains? is a substring test, or stops at the first hit, and if sends the message one of two ways. A blocked event is not forwarded and its payload is not repeated: waf.blocked carries only the subject it arrived on, so one subscriber sees every block without receiving the content that caused it.

This is plain substring matching: no regular expressions, no decoding and no case folding, so drop table in lower case passes. Treat the rule as a cheap first filter, not a full inspection layer.

Outlier gate#

The second rule forwards a reading only while it is at or below the percentile of the last 100 readings from that device. There is no fixed limit to maintain: each device learns its own normal, because state is per subject.

Ten readings in, eight out. Two things to know before relying on it:

  • The window includes the current sample. A reading that sets a new maximum for the window is above the p99 by definition, so it is held back. On a steady device that is about one message in a hundred. On a device whose readings only climb, it is every message.
  • Held-back samples still count. The 9000 above stays in the window for the next 100 samples and raises the p99 a little. A sustained run of large values therefore becomes the new normal. Add a fixed ceiling with (and (< payload-float 8192) ...) when there is a hard limit as well.

Flood detection#

The third rule watches how fast each subject publishes. rate counts messages per second over a five-second window, and transition turns the comparison into two messages: one block when the rate rises above 2 per second (more than ten messages in five seconds) and one clear when it falls back.

The eleventh message from in.event.chatty crosses the threshold; in.event.quiet has its own window and stays quiet.

  • One window per subject, with no bookkeeping. State is per call site and subject. Each subject that has ever published holds one slot, so keep the subject space bounded.
  • The verdict does not stop the traffic. The ticks above are still forwarded as clean.event.chatty. waf.flood.<subject> is advice for something that can act on it, such as revoking the publisher's credentials. To cap the flow in the rule itself, put throttle in the forwarding thread.
  • clear needs a message. A rule runs when a message arrives, so clear is published on the first message after the subject has slowed down, not at the moment the window empties.

De-identifying records#

Intermediate A bedside gateway publishes one JSON frame per reading on ward.<ward>.<patient>, with the patient's name and record number alongside the measurements. The reporting system needs the measurements and must not receive the identifiers.

What to notice:

  • An allow-list, not a block-list. json-get reads the fields the rule names. name and mrn are not removed; they are never read. A field the gateway starts sending next month is left behind too, where a pattern that hunts for identifiers would have to learn about it first. No regular expressions are involved.
  • The subject is data too. ward.icu.p4471 identifies a patient as surely as the name does. The rules publish under clean.<ward>.…, so every patient on a ward shares one output subject.
  • Coarsen what identifies. quantize 10 snaps age to the nearest ten. round does the same job for coordinates.
  • Aggregate where a total is enough. The ward average is a funnel: the first rule is :reentrant true, so its clean.icu.hr output feeds the moving-avg rule.
  • Free text gets a tripwire. A note cannot be allow-listed field by field, so the last rule holds any note containing an identifier label and reports only the subject. This is substring matching: it catches MRN 000-11-2222 and misses a bare number or a name.

This is de-identification by omission, not obfuscation. Patchbay has no hashing, tokenising or in-place masking form, so it cannot turn a record number into a stable pseudonym or forward a note with the digits starred out. If downstream needs to follow one patient across messages, issue the pseudonym at the gateway and put it in the subject. Rules like these reduce what leaves the ward; they are not a compliance control by themselves.

Making it a gate#

The rules above only decide. What makes the patchbay a gate is that the raw subjects have no other way out. Two arrangements give you that:

  • Front door. Publishers connect to monoblok, and a top-level export names the only subjects forwarded to the cluster:
  • Tap. With import, monoblok subscribes to the raw subjects on the remote server. Imported messages are private patchbay input: local subscribers see only what the rules publish.

Both are described in Export, import and JetStream, with runnable versions in NATS integration.
