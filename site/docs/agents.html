Patchbay

Write patchbays with Claude or Codex

Patchbay is small enough to fit in a coding agent's context. Install the Patchbay authoring skill, describe the stream you have and the stream you want, and it can write the rules, validate them and show you what they do with sample messages.

The portable skill#

The patchbay-authoring skill teaches Codex and Claude Code the actual DSL: forms, state, runtime differences, YAML/JSON spellings, idioms, and validation. One package serves both agents, with references loaded as needed. It works outside the Monoblok repository.

Install without a checkout#

Download patchbay-authoring.zip. The archive contains a patchbay-authoring/ directory with SKILL.md, references, and assets. Extract the whole directory, not just SKILL.md.

Run these commands in the project where you want to author patchbays. Choose the installation for your agent:

For a personal installation available across projects, extract into ~/.agents/skills for Codex or ~/.claude/skills for Claude Code instead. Install in one scope per agent to avoid duplicate entries. To update, download the current archive and replace the installed patchbay-authoring directory. Restart the agent if the skill does not appear.

The ZIP is rebuilt from the skill source whenever the docs site is built. For a version-pinned copy, use a checkout at the desired release or commit instead.

Use the skill#

In Codex, mention $patchbay-authoring. In Claude Code, invoke /patchbay-authoring. Both agents can also select it automatically when the request matches its description.

For Claude Code, use the same brief after /patchbay-authoring. Specify Tinyblok/Patchbay Lite when targeting firmware, and request YAML or JSON when wanted; EDN is the default.

Give the agent concrete input subjects, representative payloads, desired outputs, and thresholds or windows. Ask for an explanation or review in ordinary prose; ask for a file-only response when you want only the configuration text.

Install Monoblok on the same machine so the agent can run monoblok --validate and monoblok --soundcheck. Inside a Monoblok checkout it uses ./build/monoblok; Tinyblok projects should use their firmware host validator. The skill itself installs no binary or dependencies. If tools are unavailable, the agent should say so and give you the check commands.

Read generated rules before deploying them. Validation checks well-formedness; a soundcheck transcript covers only the messages supplied. Check real timing and request-reply behavior against a running target when those matter.

Use from a checkout#

The canonical package is .agents/skills/patchbay-authoring. Codex discovers it in this repository. Claude Code discovers the same package through .claude/skills/patchbay-authoring, a relative symlink. No global install is needed for work in this tree.

To install from a checkout into another project, copy the whole canonical patchbay-authoring directory into that project's .agents/skills/ or .claude/skills/. Copy the canonical directory rather than the Claude symlink, which points back into this repository.

For a tool without skill discovery, extract the ZIP and ask it to read patchbay-authoring/SKILL.md, following the relevant reference links while working on your rules. This file is now the usage guide; the former standalone prompt has moved into the skill's references.

See Codex skill documentation and Claude Code skill documentation for discovery locations and invocation details.

What to ask for#

Describe the messages, not the forms. A good brief has four things:

  • The input subjects, with their shape: coldstore.<site>.<unit>.
  • A sample payload, copied from the real stream if you can.
  • What you want out, in plain words: "only when it changes", "one alert and one all-clear", "a count".
  • The numbers: thresholds, window sizes, decimal places.

Then ask it to prove the result: "validate it, run a soundcheck with sample rows, and show me the transcript."

Read every line#

A patchbay decides which messages reach your subscribers, so treat a generated one as you would any generated configuration: scrutinise every line before it runs anywhere that matters. A file that validates is well-formed, not correct. The agent can misread the brief, and the transcript only covers the rows it chose to feed in.

Things to check by hand:

  • Filters. Does each on filter match the subjects you publish, and nothing else? * is one token and > is one or more.
  • Numbers. Are the thresholds, windows and decimal places yours, or values the agent assumed? In the example above, the brief said "last five readings", and the rule says (moving-avg 5 ...).
  • Output subjects. Where does each publish! go, and does anything export or subscribe to it?
  • :reentrant true. Every rule with it feeds its output back into the rules. Make sure that is intended.
  • Cardinality. Stateful forms keep one slot per subject. A wildcard over many subjects is many slots.
  • The cases the transcript skipped. Feed your own rows through --soundcheck: the boundary values, a malformed payload, the message that must not get through.
  • Wall-clock behaviour. Soundcheck rows arrive in one burst, so :ms windows, hold-off and throttle need a run against a real server.

If a rule is hard to read, ask the agent to explain that line, or to rewrite it more plainly. Rules that gate or filter what leaves a system (Filtering and privacy) deserve the closest reading of all.

Going further#

  • Ask for a pump script as well: a small program that publishes realistic sample traffic, so you can watch the rules against a running server. The skill includes a template for one.
  • Ask for the same file in YAML or JSON, and compare the two with the same soundcheck rows.
  • Two much larger generated patchbays are walked through in Large patchbays, with a recorded session of a coding assistant building one.
