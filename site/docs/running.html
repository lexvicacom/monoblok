Install and run

monoblok ships as a single binary for Linux (x64 or ARM64) or macOS on Apple Silicon, and as a multi-arch container image. There is no cluster to form, and the only disk it uses is an optional snapshot file for warm start.

Install#

Binary#

The release helper downloads the latest monoblok (macOS/Linux) and extracts it into the current directory. To try it out, run the unpacked binary in place:

To install it on Linux, run the bundled installer and start the systemd service:

Release binaries require the OpenSSL 3 runtime libraries. On macOS, install them with brew install openssl@3 before running monoblok. On Linux, install your distribution's OpenSSL 3 runtime package. Container images include these libraries.

The unpacked directory contains the runnable examples. Run the .sh files.

Container#

Build from source#

Requires CMake 3.22+, a compiler with C23 mode (GCC 11+ or current Apple Clang), and system OpenSSL (1.1.1 or 3.x; 4.x is not supported). libuv, nats.c and yyjson are vendored.

Command line#

A patchbay file is the only configuration. Pass it positionally or with --patchbay; .edn, .json, .yml and .yaml are accepted.

optionmeaning
--patchbay FILEpatchbay path (also accepted as the positional argument)
--host HOST / --port PORTNATS listener, default 127.0.0.1:4222
--http-host HOST / --http-port PORTenable the HTTP/SSE adapter on this port
--tls-cert FILE / --tls-key FILEenable client TLS
--auth-token-env ENVrequire a CONNECT auth_token matching the value of ENV
--auth-user-env ENV / --auth-pass-env ENVrequire a CONNECT user and password (auth)
--no-lvcdisable the $LVC.* last-value cache
--snapshot FILEload and write an LVC and patchbay state snapshot
--snapshot-every Swrite the snapshot every S seconds
--stats-tick-ms MS$STATS.* publish cadence, default 60000
--validateparse and lint the patchbay, then exit
--soundcheckread SUBJECT|payload rows from stdin and print what the rules emit
--soundcheck-labelprefix soundcheck rows with in| or out|
--soundcheck-linger-ms MSkeep clock and window state alive after soundcheck EOF, default 10000; 0 disables
--tracelog parsed client operations to stderr
--io-uring / --no-io-uringopt in to libuv's io_uring paths on Linux (off by default, for seccomp-friendly containers)
--version, -V / --help, -hprint the version or usage

--validate, --soundcheck and --trace are covered in Validate and debug rules.

Deploying#

monoblok has low hardware requirements. A 2-vCPU VM with 256 MB+ of RAM is a good starting point. monoblok runs on one application core; the operating system can still use other cores for networking and file I/O.

The systemd unit plus --snapshot handles restarts: a crash or reboot loses at most one snapshot interval of in-flight conditioning state. If you're bridging upstream, that cluster can be thought of as the system of record (anything already exported is durable there).

systemd#

Linux release tarballs ship a unit file and installer in scripts/:

Drops the binary at /usr/local/bin/monoblok, the patchbay at /etc/monoblok/patchbay.edn, snapshots under /var/lib/monoblok/state.mblk (every 10s plus on stop), and creates a monoblok system user.

Restart behaviour depends on snapshots: with --snapshot, the last-value cache and the state inside gates and windows survive a restart.

Design#

monoblok is intentionally simple at runtime: one process, one libuv loop, one application thread for protocol parsing, subject matching, patchbay evaluation, fan-out, write buffering, and LVC state. That makes the behavior predictable and keeps coordination costs out of the publish path.

For lower-level details on ownership boundaries, snapshot I/O, libuv behavior, borrowed slices, and allocation policy, see implementation notes.

Running the tests#

smoke runs the TCP server smoke, patchbay soundcheck, load-smoke, and the larger load-soak profile. load-smoke starts a temporary daemon and verifies exact TCP fan-out plus derived moving-avg, moving-sum, and count! streams.

How fast is it?#

tl;dr: It's likely to be fast enough. The saved low-end VPS run is already in the low millions of messages/sec for simple pub/sub and fan-out cases. Getting meaningful benchmarks turned out to be trickier than I first realised, though, so run scripts/bench-with-nats-server.sh on your own hardware if numbers matter to you.

The shape of the comparison vs. nats-server, though, is consistent across runs:

  • nats-server wins on pure publish throughput on big machines. Multi-threaded acceptance and a more battle-hardened parse loop both help when there's no fan-out work to spread the cost over and there are spare cores to spread it across. On small ARM VPSes the gap narrows or disappears: nats-server has less parallelism to exploit, and monoblok has less coordination overhead to pay.
  • The two are roughly comparable at low fan-out (1-10 subscribers per publish).
  • monoblok scales better with subscriber count. Its fan-out model has low per-subscriber coordination overhead. Crossover happens somewhere around 10-30 subscribers; the further past that you go, the bigger monoblok's lead.

Worth keeping in mind: nats-server has a decade of production-grade performance work behind it. Any monoblok win in these benches should be read as "the single-threaded design happens to fit this specific workload shape well," not "monoblok is faster than nats." The right tool for most pub/sub deployments is still nats-server; monoblok is for the cases where the patchbay or LVC features earn their place, and "fast enough on a small box" is a happy side-effect of the design, not the headline.

The saved benchmark runs span up to 2-18 million msgs/sec across a 2-core ARM VPS, an 8-core x86_64 VPS, and an Apple Silicon M4 Mac mini for simple publish and fan-out workloads. Treat those numbers as directional samples and trends, not capacity promises.

Patchbay overhead scales with matching rules per PUB, not total rules in the file. On Linux the benchmark scripts default to monoblok's opt-in io_uring path to match the saved runs; pass --epoll to benchmark the production-default epoll path.
