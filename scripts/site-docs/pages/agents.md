# Writing patchbays with an agent

{lede} Patchbay is small enough to fit in a coding agent's context. Give the agent the patchbay instructions, describe the stream you have and the stream you want, and it can write the rules, validate them and show you what they do with sample messages.

## Load the instructions

[`docs/AGENTS_PATCHBAY.md`](https://github.com/lexvicacom/monoblok/blob/main/docs/AGENTS_PATCHBAY.md) is a self-contained description of the language written for agents: every form, the YAML and JSON spellings, the idioms to prefer, the forms that do not exist, and the commands to check a file. It does not assume the agent has seen the monoblok repository. Without it, an agent will guess at Clojure and invent forms that fail to load.

Put it where your agent reads project instructions. Run this in the directory where you want the agent to work:

```sh
# Codex and other agents that read AGENTS.md
curl -fsSL https://raw.githubusercontent.com/lexvicacom/monoblok/main/docs/AGENTS_PATCHBAY.md >> ./AGENTS.md

# Claude Code
curl -fsSL https://raw.githubusercontent.com/lexvicacom/monoblok/main/docs/AGENTS_PATCHBAY.md >> ./CLAUDE.md
```

For other tools, paste or reference the file in the equivalent place: Cursor rules, Aider conventions or a ChatGPT project. For a one-off, save the file next to your patchbay and name it in the prompt: "Follow AGENTS_PATCHBAY.md while editing patchbay.edn."

Install monoblok on the same machine ([Install and run](running.html)). The instructions tell the agent to run `monoblok --validate` and `monoblok --soundcheck` on what it writes, and it can only do that if the binary is on the path.

## What to ask for

Describe the messages, not the forms. A good brief has four things:

- **The input subjects**, with their shape: `coldstore.<site>.<unit>`.
- **A sample payload**, copied from the real stream if you can.
- **What you want out**, in plain words: "only when it changes", "one alert and one all-clear", "a count".
- **The numbers**: thresholds, window sizes, decimal places.

Then ask it to prove the result: "validate it, run a soundcheck with sample rows, and show me the transcript."

## A worked example

The brief:

```text
Freezers publish JSON on coldstore.<site>.<unit>, like
{"temp":-18.2,"door":"closed"}.

Write a patchbay that gives me:
1. the temperature to one decimal place, only when it changes
2. a "warm" alert when the average of the last five readings reaches
   -15, and a "cold" all-clear once it is back down to -17
3. a running count of door openings

Validate it and show me a soundcheck transcript.
```

Claude wrote this file from that brief with the instructions loaded:

{{include examples/cold-store.edn}}

It picked the idioms the instructions recommend: [`json-demux!`](forms.html#json-payloads) at the head so the other rules work on scalars, `round` into `squelch` for the dashboard stream, [`hysteresis`](forms.html#hysteresis) inside `transition` for an alert that does not flap, and `rising-edge` so a door held open counts once.

Then the two checks. The first confirms the file loads:

```sh
monoblok --validate examples/cold-store.edn
```

The second runs sample rows through the rules with no server. Each row is `SUBJECT|payload`; `in` lines are the rows fed in, `out` lines are everything the rules published, including the scalars that `json-demux!` breaks out:

```sh
printf '%s\n' \
  'coldstore.leeds.f1|{"temp":-18.21,"door":"closed"}' \
  'coldstore.leeds.f1|{"temp":-18.24,"door":"closed"}' \
  'coldstore.leeds.f1|{"temp":-12.5,"door":"open"}' \
  | monoblok --soundcheck --soundcheck-label --soundcheck-linger-ms 0 examples/cold-store.edn
```

The transcript for a longer run, generated by this site's build from the same command:

```soundcheck examples/cold-store.edn
coldstore.leeds.f1|{"temp":-18.21,"door":"closed"}
coldstore.leeds.f1|{"temp":-18.24,"door":"closed"}
coldstore.leeds.f1|{"temp":-12.5,"door":"open"}
coldstore.leeds.f1|{"temp":-9.0,"door":"open"}
coldstore.leeds.f1|{"temp":-8.5,"door":"closed"}
coldstore.leeds.f1|{"temp":-19.0,"door":"closed"}
coldstore.leeds.f1|{"temp":-22.0,"door":"open"}
coldstore.leeds.f1|{"temp":-22.5,"door":"closed"}
coldstore.leeds.f1|{"temp":-22.5,"door":"closed"}
```

Reading it against the brief: the second frame rounds to the same -18.2 and publishes nothing; `warm` arrives on the fourth frame, when the five-reading average reaches -15; the door count goes to 1 and then 2, and the frame where the door stays open does not count again; `cold` arrives on the last frame, once the average is back at -17.

## Read every line

A patchbay decides which messages reach your subscribers, so treat a generated one as you would any generated configuration: scrutinise every line before it runs anywhere that matters. A file that validates is well-formed, not correct. The agent can misread the brief, and the transcript only covers the rows it chose to feed in.

Things to check by hand:

- **Filters.** Does each `on` filter match the subjects you publish, and nothing else? `*` is one token and `>` is one or more.
- **Numbers.** Are the thresholds, windows and decimal places yours, or values the agent assumed? In the example above, the brief said "last five readings", and the rule says `(moving-avg 5 ...)`.
- **Output subjects.** Where does each `publish!` go, and does anything export or subscribe to it?
- **`:reentrant true`.** Every rule with it feeds its output back into the rules. Make sure that is intended.
- **Cardinality.** Stateful forms keep one slot per subject. A wildcard over many subjects is many slots.
- **The cases the transcript skipped.** Feed your own rows through `--soundcheck`: the boundary values, a malformed payload, the message that must not get through.
- **Wall-clock behaviour.** Soundcheck rows arrive in one burst, so `:ms` windows, `hold-off` and `throttle` need a run against a real server.

If a rule is hard to read, ask the agent to explain that line, or to rewrite it more plainly. Rules that gate or filter what leaves a system ([Filtering and privacy](examples-waf.html)) deserve the closest reading of all.

## Going further

- Ask for a pump script as well: a small program that publishes realistic sample traffic, so you can watch the rules against a running server. The instructions include a skeleton for one.
- Ask for the same file in YAML or JSON, and compare the two with the same soundcheck rows.
- Two much larger generated patchbays are walked through in [Large patchbays](examples-large.html), with a [recorded session](https://lexvicacom.github.io/monoblok/show-n-tell/moonwell_linkedin_demo.html) of a coding assistant building one.
